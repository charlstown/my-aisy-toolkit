# Plan — clean-feature debe cerrar el issue solo si el plan está completo y product-spec/tech-spec quedaron alineados

Source: specs/004-clean-feature-gate-close-on-alignment/requirements.md

## Context gathered

- **This feature edits a skill-definition file, not application code.** The two copies are `ai-toolkit/default/commands/clean-feature.md` (source of truth, 307 lines as read on 2026-08-02) and `.claude/commands/clean-feature.md` (installed copy). `diff` between them today shows they are **already NOT byte-identical**: the installed copy is missing the closing sentence of Step 8 ("This is the last step of the loop. Do not print a next-step suggestion block…", added by a later, unrelated feature). FR-008 requires the two to end up "sincronizada" — this pre-existing drift must be reconciled in the same pass, not just the new gate logic, or the files stay divergent for an unrelated reason.
- **Current Step 3** (`### Step 3 — Audit the alignment of the root specs`) reads a fixed table of 7 specs (`product-spec.md`, `tech-spec.md`, `css-spec.md`, `ui-spec.md`, `infra-spec.md`, `security-spec.md`, `roadmap.md`), launches one `general-purpose` subagent per applicable spec, and only records "ALIGNED" informally — there is no persisted, per-spec, per-folder status variable today.
- **Current Step 4** (`### Step 4 — Update misaligned specs`) launches one `implementation-agent` subagent per misaligned spec and asks it to "confirm which lines you edited" at the end, but nothing downstream ever reads that confirmation or reacts to a failure — a failed edit today is silently indistinguishable from a successful one.
- **Current Step 6.5** (`### Step 6.5 — Close issues on GitHub`) closes the issue for every deleted folder that has a non-null `issue_num_{folder}` and is still open on GitHub — it does not consult Step 3/Step 4 results at all today.
- **Current Step 8** (`### Step 8 — Final summary`) template has no section for "specs pending alignment"; it only reports deleted folders, updated specs and closed issues.
- **Folder deletion (Step 6) happens before issue closing (Step 6.5)**, and the user already confirmed deletion in Step 5 (which runs after Step 3/4). Requirements.md's three acceptance scenarios and FR-001–FR-010 only mandate gating **issue closing** (Step 6.5) and the **Step 8 summary** — none of them ask to change Step 5's confirmation prompt or block Step 6's deletion. This is treated as an explicit scope boundary, not an oversight (see Decision D-03).
- **Multiple folders are processed in one run** (Steps 0-8 loop per selected folder); FR-007 and the edge case explicitly require the gate to be evaluated independently per folder, so any new state must be namespaced by folder, not global.
- FR-002/FR-003 restrict the gate strictly to `product-spec.md` and `tech-spec.md` — the other 5 specs in the Step 3 table keep their current, unconditional behavior and must never influence issue closing.

## Decisions

**D-01 — Introduce one explicit status variable per folder, scoped only to `product-spec.md`/`tech-spec.md`.**
Name: `spec_status_{spec}_{folder}` (`spec` ∈ `product-spec`, `tech-spec`). Five possible values: `not_applicable`, `aligned`, `pending` (transient, Step 3→Step 4 only), `updated`, `failed`. FR-009's four required states map to the four non-transient values (`not_applicable`, `aligned`, `updated`, `failed`); `pending` is an internal bookkeeping value that never survives past Step 4 and is never reported. The other 5 optional specs get no such variable (FR-002).

**D-02 — The gate blocks only Step 6.5 (issue closing), not Step 6 (folder deletion) or Step 5 (delete confirmation).**
Discarded: also blocking deletion or warning inside Step 5. Why: none of the three acceptance scenarios or FR-001–FR-010 ask for that, and doing so would silently expand scope beyond issue #14. This is called out explicitly as a Note in the file so a future reader doesn't assume the gate stops deletion too.

**D-03 — Gate condition: close is allowed iff both specs' status ∈ {`not_applicable`, `aligned`, `updated`}; blocked iff either is `failed`.**
This directly encodes FR-003 (not-applicable/pre-aligned never blocks), FR-004 (successfully updated never blocks) and FR-005 (a failed update blocks that folder's issue only).

**D-04 — Per-folder independence is enforced by namespacing, not by extra control flow.**
Because `spec_status_{spec}_{folder}` already carries `{folder}` in its name/scope, Step 6.5's existing per-folder loop naturally isolates one folder's `failed` status from another's — no new loop or lock is needed, just the variable's naming discipline (FR-007, edge case).

**D-05 — Batch 2 makes `.claude/commands/clean-feature.md` byte-identical to the updated `ai-toolkit/default/commands/clean-feature.md`, closing the pre-existing drift too.**
FR-008 says "sincronizada" as an end state, not "apply only the new lines" — leaving the unrelated pre-existing gap would contradict that. Future drift is explicitly out of scope for this feature (FR-008: "el mecanismo de sincronización a futuro... es setup-ai").
