# Plan: Versionado automático por título de PR

Feature Branch: 003-pr-title-auto-versioning
Requirements: specs/003-pr-title-auto-versioning/requirements.md

## Decisiones de diseño

- La lógica de cálculo de la siguiente versión se extrae a un script propio, `.github/scripts/compute-next-tag.sh`, invocado por el workflow de publicación. Esto permite testear los casos límite (FR-007 a FR-021) con bash plano, sin depender del runtime de GitHub Actions ni añadir dependencias nuevas al repo (no hay `package.json` ni test runner instalado).
- El precheck (`pr-title-check.yml`) y el cálculo de versión (`compute-next-tag.sh`) comparten la misma regex de prefijos (`^(release|feature|fix|chore):`, case-insensitive vía `shopt -s nocasematch` / `tr` a minúsculas) para que ambos apliquen exactamente la tabla de `CLAUDE.md`.
- `actions/checkout` se configura con `fetch-depth: 0` en el workflow de publicación para garantizar que todos los tags existentes estén disponibles al listarlos con `git tag -l`.
- El "último tag" se calcula con `git tag -l 'v*' | grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$' | sort -V | tail -n1`, que ignora estrictamente cualquier tag que no sea `vX.Y.Z` (FR-018) y ordena por semver real, no por fecha de creación.
- El job de publicación de tag se restringe a PRs cuya `base.ref == 'main'` (además de `merged == true`), para no calcular versión en merges hacia otras ramas si las hubiera.
- `concurrency: { group: publish-version-tag, cancel-in-progress: false }`: al no cancelar ejecuciones en curso, dos merges casi simultáneos se serializan (uno espera a que el otro termine de publicar su tag) en vez de competir o cancelarse a medio push (FR-017).
- Autenticación de push: se usa el `GITHUB_TOKEN` por defecto con `permissions: contents: write` a nivel de workflow; `actions/checkout` ya deja el credential helper configurado, sin necesidad de PAT (FR-020).
- El required status check de branch protection solo puede seleccionarse en GitHub una vez que el contexto ha corrido al menos una vez en el repo real. Por eso la tarea de configurar branch protection (Batch 4) se secuencia **después** de mergear/ejecutar por primera vez el workflow de precheck.
- Trigger confirmado por el usuario durante la planificación (2026-08-02): el workflow de publicación de tag se dispara por el evento `pull_request` con `types: [closed]` y condición `merged == true` — NO por `push` a `main` — para poder leer directamente `github.event.pull_request.title` sin llamadas extra a la API de GitHub (FR-005).

## Batch 2 — Script y workflow de publicación de tag semver

- [x] @code-developer · Implementar script de cálculo de tag: crear `.github/scripts/compute-next-tag.sh` (ejecutable, `chmod +x`), que reciba el título de la PR como argumento y, ejecutándose dentro de un checkout con historial completo de tags: (1) determine el tipo de bump a partir del prefijo (case-insensitive: `release:`→major, `feature:`→minor, `fix:`→patch, `chore:`→sin publicación, cualquier otro prefijo→fallo explícito con `exit 1` y mensaje `::error::`, cumpliendo FR-016); (2) calcule el último tag válido con `git tag -l 'v*' | grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$' | sort -V | tail -n1`, ignorando tags que no sean estrictamente `vX.Y.Z` (FR-018); (3) si no hay tag previo, aplique las reglas de versión inicial (`v0.1.0` para `feature:`/`fix:`, `v1.0.0` para `release:`, FR-011/FR-012); si hay tag previo, incremente el componente correspondiente y ponga a cero los inferiores (FR-007/FR-008/FR-009); (4) si el tag calculado ya existe (`git rev-parse refs/tags/$new_tag`), falle explícitamente con `exit 1` sin sobrescribir (FR-021); (5) si el prefijo es `chore:`, termine en éxito sin crear ni publicar ningún tag (FR-010); (6) en cualquier otro caso, cree el tag anotado y haga `git push origin $new_tag` (configurando `user.name`/`user.email` de `github-actions[bot]` para el commit del tag), sin crear un GitHub Release (FR-019).
- [x] @code-developer · Crear workflow de publicación de tag: crear `.github/workflows/publish-version-tag.yml` disparado por `pull_request` con `types: [closed]`, con `permissions: { contents: write }` y `concurrency: { group: publish-version-tag, cancel-in-progress: false }` a nivel de workflow. Job `publish-tag` con `name: "Compute and publish semver tag"` y condición `if: github.event.pull_request.merged == true && github.event.pull_request.base.ref == 'main'`. Steps: `actions/checkout@v4` con `fetch-depth: 0` (para tener todos los tags disponibles), seguido de la ejecución de `.github/scripts/compute-next-tag.sh "${{ github.event.pull_request.title }}"`. No debe implementar ninguna lógica adicional de fallback ante bypass del precheck (FR-015): si el título no tiene prefijo válido en el momento del merge, debe fallar, punto — no reintentar ni inferir.
- [x] @test-developer · Escribir tests de la lógica de versión: crear un script de test en bash plano (p. ej. `.github/scripts/compute-next-tag.test.sh`, sin añadir runners nuevos al repo) que, usando repos git temporales (`git init` en un directorio temporal, creando tags con `git tag`), ejercite `compute-next-tag.sh` contra los siguientes casos y compare la salida/tag creado con el esperado mediante aserciones simples: (a) tag previo `v0.3.1` + `feature:` → `v0.4.0`; (b) `v0.3.1` + `fix:` → `v0.3.2`; (c) `v0.3.1` + `release:` → `v1.0.0`; (d) `v0.3.1` + `chore:` → no se publica tag y el script termina en éxito; (e) sin tags previos + `feature:` o `fix:` → `v0.1.0`; (f) sin tags previos + `release:` → `v1.0.0`; (g) título sin prefijo válido → el script falla (`exit != 0`); (h) tag calculado ya existente → el script falla sin sobrescribir; (i) tags mal formados en el repo (p. ej. `v1.2`, `release-2024`, `1.2.3`) → deben ignorarse por completo al calcular el último tag. No ejecutar este script en CI todavía (eso lo hace @tester/@code-developer al integrar); entregar el script listo y documentar cómo correrlo localmente (`bash .github/scripts/compute-next-tag.test.sh`).
