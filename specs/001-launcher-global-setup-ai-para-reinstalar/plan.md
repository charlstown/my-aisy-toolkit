# Plan — Launcher global /setup-ai para reinstalar sin repetir el one-liner

Source: specs/001-launcher-global-setup-ai-para-reinstalar/requirements.md
Issue: #8 (`[FEAT] Añadir launcher global /setup-ai para reinstalar sin repetir el one-liner`)

## Contexto verificado

Todo lo que sigue está comprobado leyendo los ficheros del repo y el entorno el 2026-08-01. Lo que es suposición está marcado como tal.

- **`setup-ai.md` (raíz, 255 líneas) es hoy un fichero de instrucciones en lenguaje natural con 5 pasos + un cierre**: Step 1 (preguntar agente destino y perfil), Step 2 (fetch `catalog.yaml`), Step 3 (fetch de cada fichero del perfil), Step 4 (escribir para Claude Code), Step 5 (traducir y escribir para Codex CLI, L181-219) y `### Wrap up — Tell the user what happened` (L221-255). El punto de inserción natural del nuevo paso es **entre L219 y L221**.
- **`setup-ai.md` prohíbe explícitamente hoy escribir fuera del repo**: L7-8 (`Side effects are limited to writing files inside .claude/ and/or .codex/ in your repo. Nothing else is touched.`) y L52 (`- Do **not** write, move, or delete anything outside \`.claude/\` and \`.codex/\` in the user's repo.`). **Esta feature rompe ese contrato de forma deliberada** (escribe en `~/`), así que ambas líneas deben modificarse o la instrucción nueva contradice la regla que el propio fichero le da al agente. Es la restricción estructural más importante del plan.
- **La misma promesa está replicada en 4 sitios más**, todos verificados por grep: `README.md` L41 y L132, `README-ES.md` L41 y L132, y `specs/product-spec.md` L72-73 (`> [!warning] Side effect / Writes/overwrites files inside .claude/ and/or .codex/ in the target repo. Does not touch application code or other folders.`). Si no se tocan, el README afirma algo falso en cuanto la feature entre.
- **`setup-ai.md` se declara autocontenido** (L41-42: `Everything below is self-contained — no other file needs to be fetched for the agent to know what to do.`) porque existe la vía copy-paste (Option 2). Esto condiciona dónde puede vivir la plantilla del launcher (ver D-01).
- **Claude Code: comandos de usuario en `~/.claude/commands/`** — verificado en la máquina del mantenedor: el directorio existe y contiene `grill-me.md` y **`setup-ai.md`**. Ese `setup-ai.md` global **ya existente NO es de este producto**: es la versión legacy del vault local del mantenedor (frontmatter con `allowed-tools: Bash(powershell:*)`, apunta a `D:\MisProyectos\0_TEMPLATES\SETUP-AI` y ejecuta `sync.ps1`). Colisión real de nombre y ruta, ver R-01 y D-05.
- **Codex CLI: el directorio global no está cerrado por la documentación oficial.** Verificado: en la máquina existe `~/.codex/` con `auth.json`, `config.toml`, `rules/`, `memories/` y **`skills/` (vacío)**; no existe `~/.codex/prompts/` ni `~/.agents/`. La doc oficial de skills (learn.chatgpt.com/docs/build-skills) documenta `$HOME/.agents/skills` como ubicación de usuario, mientras que fuentes de comunidad y el propio binario apuntan también a `~/.codex/skills/`. La doc de custom prompts (`~/.codex/prompts/`, invocados como `/prompts:<name>`) los declara **deprecados** a favor de skills. `codex` **no está en el PATH de esta máquina**, así que no se ha podido verificar en ejecución. Ver D-04 y R-02.
- **Codex invoca skills con `$nombre`, no con `/nombre`** (doc oficial: `$skill-name`, listado con `/skills`). El issue habla siempre de `/setup-ai`; en Codex el comando real será `$setup-ai`. Hay que decirlo en las specs para no prometer algo que no ocurre.
- **`setup-ai.md` ya escribe en formato Codex a nivel repo como `.codex/skills/<name>/SKILL.md`** (L193). El equivalente global coherente con esa convención es `~/.codex/skills/<name>/SKILL.md`.
- **`catalog.yaml` declara 11 commands + 6 agents del perfil `default`**. El launcher **no** es una skill del catálogo (no se instala por repo, se instala una vez a nivel usuario), así que `catalog.yaml` **no cambia** y los contadores `skills-11` / `agents-6` de los READMEs tampoco.
- **ADR existentes en `specs/tech-spec.md`: ADR-001 a ADR-005.** ADR-004 (`Target agent detection always by explicit question`) dice que el agente destino **nunca** se infiere de las carpetas presentes. Esta feature necesita detectar qué agentes existen **en el entorno del usuario** (`~/.claude`, `~/.codex`), que es una cosa distinta; hay que redactarlo con cuidado para no dar pie a que un agente se salte el Step 1. Ver D-03.
- **Colisión con la feature 002** (`specs/002-versionado-del-repo-version-changelog-git-tags/requirements.md`): su FR-008 también pide crear **ADR-006** en `specs/tech-spec.md`, y su FR-006 toca los badges de `README.md` / `README-ES.md`. Los dos planes escriben en los mismos ficheros. Ver R-06.

## Decisiones

**D-01 — Las dos plantillas del launcher viven embebidas literalmente dentro de `setup-ai.md`, no en un fichero aparte del repo.**
Descartado: (a) `ai-toolkit/launcher/claude.md` + `codex.md` fetcheados en el momento de escribir; (b) añadir el launcher a `catalog.yaml`.
Por qué: `setup-ai.md` L41-42 promete ser autocontenido para la vía copy-paste; un fichero externo rompe esa vía y añade dos modos de fallo de red nuevos. Y `catalog.yaml` es, por ADR-003, el manifiesto de qué entra **en cada repo** por perfil: meter ahí el launcher lo instalaría dentro de `.claude/commands/` del repo destino, que es exactamente lo contrario de lo que pide el issue. Las plantillas son cortas (≈15 líneas), el coste de duplicación es nulo.

**D-02 — El contenido del launcher es un puntero puro: frontmatter + "fetch esta URL y sigue las instrucciones desde el Step 1".**
Descartado: copiar `setup-ai.md` literalmente en el fichero global (lo prohíbe FR-002 explícitamente), o embeber una versión resumida del catálogo.
Por qué: FR-004 y el principio "Always the latest version" de `product-spec.md`. Un launcher sin lógica propia no puede quedarse obsoleto: toda la lógica se re-fetchea viva en cada invocación. Esto además **cierra el NEEDS CLARIFICATION sobre "launcher desactualizado"** de los Edge Cases (ver D-06).

**D-03 — La detección de "qué agentes hay" se hace por presencia del directorio de usuario (`~/.claude/`, `~/.codex/`), y es independiente de la pregunta del Step 1.**
Descartado: (a) reutilizar la respuesta del Step 1 como si fuera el agente del entorno; (b) preguntar al usuario para qué agentes quiere el launcher.
Por qué: la aclaración del usuario pide escribir **solo para el agente presente** para no dejar ficheros huérfanos, y el Step 1 responde a otra pregunta distinta (para qué formato se instala **en el repo**, que puede no coincidir con el agente que está ejecutando). (b) añade una segunda pregunta y fricción justo en el paso cuyo objetivo es reducirla. **Riesgo de contagio con ADR-004**: hay que escribir en `setup-ai.md` una frase explícita de que esta detección aplica SOLO al launcher global y nunca sustituye la pregunta del Step 1.

**D-04 — Ruta Codex: `~/.codex/skills/setup-ai/SKILL.md` como destino primario, con `~/.agents/skills/setup-ai/SKILL.md` como fallback documentado.**
Descartado: (a) solo `~/.agents/skills/` (lo que dice la doc oficial); (b) `~/.codex/prompts/setup-ai.md` (custom prompts).
Por qué: (b) está deprecado oficialmente. Entre (a) y el primario, `~/.codex/skills/` es el que **existe realmente** en la máquina objetivo, es el que replica la convención `.codex/skills/<name>/SKILL.md` que `setup-ai.md` ya usa a nivel repo (L193), y no obliga al usuario a conocer un tercer árbol de directorios. La regla operativa escrita en `setup-ai.md` será: si existe `~/.codex/`, escribe en `~/.codex/skills/setup-ai/SKILL.md`; si no existe `~/.codex/` pero sí `~/.agents/`, escribe en `~/.agents/skills/setup-ai/SKILL.md`. Para **detectar si ya existe** se comprueban ambas rutas. Decisión revisable en cuanto se pueda probar contra un Codex real (ver R-02).

**D-05 — Si ya hay un fichero en la ruta destino: no se pregunta, no se sobrescribe, y se reporta en el Wrap up.**
Descartado: (a) sobrescribir siempre; (b) callarse por completo.
Por qué: FR-006 dice `MUST NOT` volver a preguntar y FR-009 fija la detección por existencia del fichero, así que sobrescribir queda fuera. Pero (b) es peligroso en el caso real ya verificado: en la máquina del mantenedor hay un `~/.claude/commands/setup-ai.md` **legacy y ajeno a este producto** (R-01); si el instalador se calla, el usuario creerá que tiene el launcher nuevo y tendrá el viejo. Una línea en el Wrap up ("ya existía un `/setup-ai` global, no lo he tocado") cumple FR-006 al pie de la letra y elimina la sorpresa silenciosa. No se inspecciona el contenido del fichero: FR-009 dice existencia, y meter detección por marcador sería ampliar alcance.

**D-06 — El launcher nunca se auto-actualiza ni se versiona.**
Cierra el Edge Case abierto "¿qué pasa si el launcher existe pero está desactualizado?".
Por qué: por D-02 el launcher no tiene contenido que pueda envejecer — es una URL y una instrucción. Si algún día su formato tuviera que cambiar, el remedio documentado es que el usuario borre el fichero y vuelva a ejecutar el one-liner. Se documenta como limitación conocida en `tech-spec.md`, no como mecanismo a construir.

**D-07 — Un fallo al escribir el launcher global nunca aborta ni revierte la instalación del catálogo.**
Cierra el Edge Case "manejo de errores al escribir el launcher global".
Por qué: cuando se llega al Step 6 el catálogo ya está instalado y esa es la promesa principal del one-liner; el launcher es un extra opcional. Mismo criterio de resiliencia por-fichero que ya usa el Step 3 (`FR-012`: reintentar, informar, seguir). Se informa en el Wrap up con la razón real (permisos, ruta inexistente...), sin reintentos ni rutas alternativas inventadas.

**D-08 — Si el fetch de `setup-ai.md` falla al invocar el launcher, se aborta y no se escribe nada.**
Cierra el Edge Case "manejo de errores de red al invocar el launcher global".
Por qué: es exactamente la misma situación que el Step 2 actual (sin manifiesto no hay nada que instalar) y ya está resuelta ahí con "abort, informa, no escribas nada, no uses caché". El launcher reusa esa política en vez de inventar una nueva.

**D-09 — La supresión de la pregunta cuando se viene del launcher se implementa por partida doble: instrucción explícita en la plantilla + el propio chequeo de existencia.**
Descartado: un parámetro en la URL (`?from=launcher`) o una URL alternativa del fichero.
Por qué: `raw.githubusercontent.com` sirve el mismo contenido y un query param solo funcionaría si el agente lo interpretara, cosa que no está garantizada. La redundancia sale gratis: si se viene del launcher, el fichero launcher existe por definición, así que FR-009 ya suprime la pregunta; la frase en la plantilla es la garantía explícita que pide FR-005.

**D-10 — No se toca `catalog.yaml`, ni los contadores de skills/agents, ni se sube el badge de versión.**
Por qué: el launcher no es una skill del catálogo y ningún FR de esta feature pide bump de versión (a diferencia de la feature anterior, cuyo FR-008 sí lo pedía). La feature 002 va a introducir `VERSION` + `CHANGELOG.md`; decidir aquí un número de versión invadiría ese alcance. Se deja como punto abierto para el usuario (U-03).

**Abierto / no cerrado aquí**

- **U-01 — Ruta global real de Codex CLI.** D-04 elige la más probable con la evidencia disponible, pero no se ha podido ejecutar `codex` en esta máquina. Hasta que se pruebe, el soporte Codex de esta feature es best-effort igual que el resto (ADR-002).
- **U-02 — Nombre del comando en Codex.** Será `$setup-ai`, no `/setup-ai`. El issue y las specs hablan de `/setup-ai`; se documenta la diferencia, pero si el usuario prefiere otro nombre de skill para Codex, hay que decirlo antes del Batch 2.
- **U-03 — Bump de versión / entrada de changelog.** No lo pide ningún FR y choca con la feature 002. Sin hacer.
- **U-04 — Documentar el launcher en el README.** FR-007 solo obliga a `product-spec.md` y `tech-spec.md`. El Batch 4 corrige el README **únicamente** donde afirma algo que dejaría de ser cierto (los efectos secundarios). Añadir una sección de marketing del launcher al README es una mejora aparte que no se asume aquí.

- **R-01 (alto) — Colisión con el `/setup-ai` legacy del mantenedor.** En esta máquina ya existe `~/.claude/commands/setup-ai.md`, pero es el comando antiguo que sincroniza desde `D:\MisProyectos\0_TEMPLATES\SETUP-AI` vía `sync.ps1`. Mitigación: D-05 lo reporta en el Wrap up en vez de callarlo, y el Batch 5 prohíbe explícitamente tocar el HOME real.
- **R-02 (alto) — La ruta global de Codex puede ser la equivocada.** La doc oficial dice `~/.agents/skills`, la máquina tiene `~/.codex/skills`, y `codex` no está instalado aquí para salir de dudas. Si D-04 falla, el launcher de Codex se escribe donde Codex no lo lee: fichero inerte, no destructivo. Mitigación: fallback a `~/.agents/skills/`, detección en ambas rutas, y limitación documentada. Validar en cuanto haya un Codex real a mano — es lo primero que hay que comprobar si alguien reporta que `$setup-ai` no aparece.
