## Decisions

**D-01 — Duplicate the block verbatim in each skill file; no shared template file.**
Discarded: (a) a single `next-step-block.md` referenced from each skill; (b) a new dedicated skill invoked at the end of the others.
Why: skills are distributed **one file at a time** by `setup-ai` into a target repo's `.claude/commands/`; a cross-file reference would break on install. The repo already duplicates the `## Language` boilerplate in all 11 files — this follows the established convention.

**D-02 — The block is authored in English in the skill files, with an explicit instruction to render it in the user's language.**
Discarded: hardcoding the Spanish literal `✅ Listo. Siguiente paso sugerido:` from Acceptance Scenario 1.
Why: every skill file is authored in English and its `## Language` section forbids forcing the interaction into any one language. Hardcoding Spanish would break English-speaking users of the distributed kit and contradict a rule present in all 11 files. The requirement's Spanish string is honoured as the *reference rendering* that the Batch 0 template must reproduce when the user speaks Spanish.

**D-03 — The block goes *inside* the execution protocol (last step), not appended after `## Constraints`.**
Discarded: a uniform `## Next step` H2 at the end of every file.
Why: `## Constraints` / `## Formatting notes` are reference material an agent reads as rules, not as actions. A closing message is an action and belongs to the ordered step list. For the three files with no closing step (`product-spec`, `tech-spec`, `roadmap`), a new numbered final step is created rather than bolting the block onto the "write the file" step, so the write instruction stays clean.

**D-04 — Success gating (FR-007) is written as an explicit precondition sentence per file, naming that file's own non-success exits.**
Discarded: a single generic "only on success" clause copy-pasted identically.
Why: each skill has different early-stop paths (`constitution` Step 0 "Cancel"; `plan-feature` Step 1 "no requirements.md exists → inform the user and stop"; `implement-feature` blocked/failed tasks; `clean-feature` "user chose not to delete"). A generic clause leaves the agent guessing; naming the exits makes FR-007 verifiable per file.

**D-05 — `product-spec` and `tech-spec` suppress their block when they were invoked as a step of `/constitution`.**
Discarded: (a) blocks always fire (produces 3 blocks per `/constitution` run, 2 of them pointing to steps `constitution` is already doing); (b) `product-spec`/`tech-spec` never show a block (breaks FR-001 and the standalone row of the FR-005 table).
Why: FR-005's own note states the `product-spec` row applies "only when the user runs that skill independently". The suppression rule is one sentence in each of the two files and preserves both requirements. `constitution`'s Step 3 block remains the single closing block of a constitution run.

**D-06 — `clean-feature` receives an explicit "do not print a next-step block" instruction; `new-issue` and `grill-me` are left byte-identical and their exclusion is verified by diff.**
Discarded: leaving all three untouched.
Why: `clean-feature` sits at the tail of the same chain and its `### Step 8 — Final summary` is stylistically a sibling of the eight files that *will* have a block — an agent is plausibly tempted to improvise one, and the README even frames the workflow as a loop (`README.md` L68, L71: "back to constitution"). One negative sentence closes that hole and makes FR-006 testable. `new-issue`/`grill-me` are outside the chain and read in isolation, so no in-file note is needed; the exclusion is enforced as a verification task in Batch 2 (FR-004 "explicitly excluded" is satisfied by the documented mapping + the verified zero-diff).

**D-07 — `implement-feature` prints the block exactly once, at the true end of the run, and never when any plan has blocked or failed tasks.**
Discarded: one block per plan inside `#### 5c`.
Why: a multi-plan run would emit N blocks. FR-002 caps the block at 1-3 options for one closing moment, and FR-007 treats a partial result as non-success — blocked tasks are exactly that (the existing text already says `"Review the blocks and run /implement-feature again to continue."`).

**D-08 — The block suggests; it never auto-invokes the next skill.**
Discarded: chaining the next skill automatically.
Why: `specify-feature.md` L177 states the opposite rule explicitly ("Do not invoke `/clarify-feature` or `/plan-feature` automatically"). The requirement asks for a *suggestion*, and auto-chaining would silently expand every skill's side effects.

**D-09 — Version bump `1.0` → `1.1`.**
Discarded: `1.0.1` (the badge uses a 2-segment scheme, `X.Y`, per FR-008) and `2.0` (nothing breaks for existing installs).
Why: additive, user-visible behaviour change across the whole catalog with no breaking change. The `updated-` date badge is refreshed in the same edit for internal consistency; `skills-11` and `agents-6` stay untouched (no skill added).

### Risks

- **R-01 (high) — Template drift across 9 files.** Nine independent mechanical edits of hand-written text drift easily. Mitigated by locking the literal in Batch 0 *before* any edit and by the Batch 2 grep-level check plus the Batch 4 consistency review. If drift shows up anyway, the fix is cheap (re-copy from the Batch 0 artifact).
- **R-02 (high) — Triple block inside `/constitution`.** The most likely functional bug in this feature (D-05). Batch 4 check (d) exists specifically to catch it; validate it early, ideally right after the `product-spec.md` and `tech-spec.md` tasks.
- **R-03 (medium) — FR-007 gating is only as reliable as the wording.** These are instructions to an LLM, not code: "success" cannot be enforced, only described. Naming each file's concrete exit paths (D-04) is the mitigation; residual risk is accepted.
- **R-04 (medium) — No automated test harness exists.** Nothing in this repo executes skills, so SC-001/SC-002 can only be verified statically (Batch 2) plus, optionally, by the user running one skill end to end. SC-003 (users know what to do next) is not verifiable inside this feature at all.
- **R-05 (low) — `.claude/commands/` drift** (U-03). The repo's own copy stays behind; harmless for the distributed catalog, mildly confusing when dogfooding.
- **R-06 (low) — Assumption that `constitution`'s suppression rule is evaluable.** It assumes a sub-skill can tell it was invoked by `/constitution`. If in practice it cannot, the fallback is to move the suppression to `constitution.md` (instruct it to tell the sub-skills to skip their closing block) — a one-line change in a single file.
