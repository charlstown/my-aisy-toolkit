## 2. Decisions

### D-01 — New skill source files live under a dedicated `ai-toolkit/ui-ux/commands/` folder, not duplicated into `ai-toolkit/default/`

**Decision:** create `ai-toolkit/ui-ux/commands/ui-spec.md` and `ai-toolkit/ui-ux/commands/clarify-uix.md` as new files. The `ui-ux` profile's `commands:` list in `catalog.yaml` references the **existing** 10 `ai-toolkit/default/commands/*.md` paths unchanged, plus these 2 new paths under `ai-toolkit/ui-ux/commands/`.
**Alternative discarded:** copying the 10 default skill files' content into a new `ai-toolkit/ui-ux/` tree, or adding `ui-spec.md`/`clarify-uix.md` directly inside `ai-toolkit/default/commands/` (which would silently add them to the `default` profile too, violating FR-001/FR-002 — `default` must stay unchanged).
**Why:** `catalog.yaml`'s `commands`/`agents` entries are a flat list of source paths (tech-spec ADR-003) with no requirement that a profile's files live in one folder; reusing the existing `default` paths verbatim is the only way to guarantee "ui-ux equals default's lists plus 2 files" (FR-001) without a second copy that can drift out of sync with `default`'s originals.

### D-02 — No changes to `setup-ai.md` are required for FR-002 / SC-002

**Decision:** Step 1's profile question and Step 2's catalog read are already generic ("listing every profile the catalog declares with its file counts"); adding the `ui-ux` key to `catalog.yaml`, positioned after `default:`, is sufficient by itself to make `ui-ux` appear "alongside `default`, listed after `default`, with its own accurate file/skill count, no special visual treatment."
**Why:** verified directly against `setup-ai.md` L80-123 — nothing there special-cases `default`, hardcodes a profile count, or depends on folder structure beyond concatenating the catalog's own path strings. Editing it would be unnecessary scope creep and would risk introducing a second source of truth for something the file already computes dynamically. This is confirmed mechanically in Batch 4 by `@tester` re-reading Step 1's exact wording against FR-002.

### D-03 — `ui-spec` is a generalized rewrite of the facturito reference, not a copy

**Decision:** `ai-toolkit/ui-ux/commands/ui-spec.md` follows the reference file's **structure and staging** (Language boilerplate identical to this repo's other skills → read-context step → identify screen → content-structure pass + initial ASCII mockup → Round 1 (structure/content, gated) → Round 2 (interaction/states/microcopy) → Round 3 (devices/edge cases/accessibility) → self-critique pass → write `specs/ui-spec.md`), but rewrites every facturito-specific reference: drop the `specs/css-spec.md` dependency (not a file this toolkit's target repos are assumed to have) and describe aesthetic decisions as "belonging to the project's own design system, if any exists" instead; keep reading `specs/product-spec.md`/`specs/tech-spec.md`/`README.md` for context exactly as the reference does (those are generic, not facturito-specific); keep the 4 ready-made per-screen-type question sets (List/Log, Form/Onboarding, Modal/Bottom Sheet, Dashboard/Summary), reworded generically.
**Why:** FR-003 explicitly requires this generalization ("adapted to write `specs/ui-spec.md` in a way that generalizes beyond the reference project... its concrete interrogation questions... MUST be adapted from that reference file's structure rather than designed from scratch") and the Assumptions section is explicit that the reference is "read-only... not to be copied verbatim."

### D-04 — `clarify-uix` targets a `requirements.md` exactly like `clarify-feature`, but replaces "extract pre-itemized gap bullets" with "generate N top-down UI/UX questions"

**Decision:** `clarify-uix` reuses `clarify-feature`'s Step 0 target-resolution (explicit path → folder → feature-slug fragment → `Glob specs/*/requirements.md` discovery when nothing is indicated) and its fold-into-document / gap-section update-or-remove mechanics (Steps 2d/2e of `clarify-feature`) verbatim in spirit. What's new and specific to `clarify-uix`: **before** building any question, it asks the fixed 3-option question-count question (4/8/12, one marked "(recommended)"), then it builds its own question set from scratch — top-down, staged like `ui-spec`'s rounds (content structure → layout → interaction/states → devices/accessibility) — sized to the chosen count (a proportional split across the 4 stages, e.g. 4→1 each, 8→2 each, 12→3 each, with any remainder going to the interaction/states stage since it is usually where the most product-specific ambiguity lives), run in rounds of at most 4 questions per `AskUserQuestion` call and gated the same way `ui-spec` gates Round 1→2 (do not open a later stage while an earlier stage's answer leaves a structural ambiguity open).
**Alternative discarded:** making `clarify-uix` operate on `specs/ui-spec.md` instead of `requirements.md`. Discarded because FR-005 says it "mirrors `clarify-feature`'s purpose," and `clarify-feature`'s purpose is specifically closing gaps in `requirements.md` files — `ui-spec` already owns writing `specs/ui-spec.md`.
**Why:** this is the most direct reading of FR-005/FR-006 that reuses proven, already-verified mechanics (`clarify-feature`) instead of inventing a new target-resolution or document-folding scheme, while still giving `clarify-uix` its own distinct value (user-chosen length, top-down staged UI/UX question set) instead of being a thin parameterization of `clarify-feature`.

### D-05 — The "(recommended)" option is chosen by a stated, checkable heuristic, not left to model discretion

**Decision:** the recommendation logic must be written out explicitly in the skill file as a short, checkable heuristic based on signals already available in the target `requirements.md` (and `specs/ui-spec.md` if present): count of distinct screens/flows mentioned, count of Functional Requirements touching UI/UX, and whether structural ambiguities (missing content-structure decisions) are still open. Roughly: few/no UI signals or a single simple screen → recommend 4; a handful of screens or a screen with several states/interactions → recommend 8; multiple screens, flows, or heavy interaction/accessibility surface → recommend 12. This heuristic and its 3 buckets must be written into the skill file itself (not left implicit), since FR-006 requires the skill to "analyze how much UI/UX scope or complexity is at hand" every time it runs, not just once.
**Why:** without an explicit, written rule, two different runs of the same skill could recommend differently for the same input, which would fail SC-004's requirement that the recommendation be scope-based rather than arbitrary. Writing the heuristic directly into the skill's instructions is the same approach this repo already uses elsewhere for judgment calls (e.g. `plan-feature.md`'s gap-vs-not-a-gap table).

### D-06 — Out of scope: `setup-ai.md`, `README.md`, `specs/product-spec.md`, `specs/tech-spec.md`, `.claude/commands/`, and `packs.utils`

**Decision:** none of these are touched by this plan.
**Why:** `setup-ai.md` needs no edit (D-02). `README.md`/`specs/product-spec.md`/`specs/tech-spec.md` document only `default` today and will go stale the moment `ui-ux` ships, but this repo's established convention (see `fix-setup-ai-step-6-…` plan, D-06) is to leave root-spec/README realignment to `/clean-feature` after the feature closes, not to bundle it into the feature plan. `.claude/commands/` mirrors only what this repo installs on itself (`default`), and `ui-ux` is not installed on this repo, so there is no internal copy to create or sync. `packs.utils` belongs to the sibling feature `002-add-optional-utils-skill-pack-…`, which explicitly excludes `ui-ux` from its own scope (FR-011) — the two mechanisms are confirmed independent per the requirements' own Edge Cases section.
